# 経費・購入申請アプリ

TSS AI Coreの構想文書とは独立した、架空データ専用のローカル試作です。本番用ではありません。顧客の要望はユーザーを通じた代理情報であり、追加仕様の有効性は未検証です。

- リポジトリ： https://github.com/skaburagi-ui/expense-app

## 起動

Node.jsがあるPCで、このディレクトリに移動して実行します。依存パッケージの追加は不要です。

Windowsでは `start-local.cmd` をダブルクリックしても起動できます。

```powershell
npm start
```

ブラウザーで http://127.0.0.1:4173 を開きます。停止は Ctrl+C。動作検証は `npm test`。

## 試し方

1. 「試用保守担当」→「設定 → 承認ルート」で、パターンの作成・工程の並べ替え・下書き保存・プレビュー・新版公開・新規利用停止ができます。公開した版を申請種類に割り当てます。初期は仮払い・出張費・経費精算が「社長直接承認」、購入が「経理確認あり」です。
2. 「社員」で申請種類を選ぶと、割当済みの公開ルートで提出します。社員が簡略ルートを選ぶことはできません。見積書と領収書を区別し、購入前と仮払い支給前には領収書を要求しません。
3. 購入は「経理」の事前確認→「社長」の承認→「社員」の購入実績・領収書登録→「経理」の精算記録へ進みます。経理の2工程は別の工程IDです。
4. 仮払いは「社長」承認→「経理」の支給記録で「支給済み」となります。後日の出張費・経費精算に紐付けると、支給済額・実費・追加支給／返金の差額を表示します。処理日・方法・担当者・金額を記録し、二重紐付け・二重処理は拒否します。実際の送金はありません。
5. 理由付きの差し戻し後の修正と購入前変更は、提出時に保存したルートの最初から再確認・再承認します。購入前の理由付き中止と、社長による理由付き却下も可能です。
6. 購入後の増額・品目用途変更も再確認・再承認します。購入実績と領収書は保持し、再購入・再登録を要求しません。新規提出後に設定を変更・停止しても、既存申請のルートは変わりません。
7. 一覧・詳細で現在工程・担当・進捗を確認できます。履歴には操作時点の内容・変更前後と添付本体を保持します。旧履歴に添付名しかなかったものは復元できません。

## 要件と仮の運用

- 伺った要件：10名程度、社内ネットワークのみ、PC・スマホ、社員→社長→経理、出張費精算・備品購入前申請。
- 追加要望（2026-11-18、承認ルートの設計変更はユーザー承認済み）：仮払い申請と、申請種類ごとの承認ルートパターン設定。パターン設定画面・可変ルート・仮払い処理を2026-11-18のローカル試作へ追加しました。旧申請は提出時の固定ルートを維持します。承認範囲と最新設計はDESIGN.mdを参照。
- 試作で採用した案：精算時の領収書必須、増額時の再承認、差し戻し後は保存済みルートの先頭から再確認・再承認。お客様による確認は未実施です。
- 検証する仮説：経理の中継作業が減ること、社長が入力内容だけで判断できること、差し戻しによる往復が増えないこと。

## 制約

- 保存先はこのブラウザーのlocalStorage（新形式 `expense-prototype-v2`）です。旧キー `expense-prototype-v1` は変更・削除せず保全し、初回のみ旧申請・履歴・添付を読み取ります。欠損・不正データや移行保存失敗は表示して停止し、自動リセットしません。PC・スマホ・別ブラウザー間で共有されません。
- 役割切り替えは操作体験用で、ログインや権限制御ではありません。全申請を同じサンプル社員のものとして扱います。
- 実名・個人情報・実際の領収書を入力しないでください。送金・会計連携・正式な証憑保存は実装していません。
- 添付は画像またはPDF、1申請合計3MBまで。履歴にも添付を保持するため、保存容量はブラウザー依存で上限に達する場合があります。保存失敗は表示し、操作を成功扱いにしません。初期サンプルに添付はありません。
- 試作サーバーはPC内（127.0.0.1）だけで待ち受けます。社内LANへの公開、ファイアウォール変更は行っていません。
- スマホ幅の表示を確認できるレスポンシブ画面ですが、実機での社内Wi-Fi利用は未検証です。

本番化では共有サーバー・認証・権限・添付保管・バックアップ・社内LANの接続設定を別途設計し、社内での公開範囲を確認します。
