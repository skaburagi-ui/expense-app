# 標準ワークフロー

```text
人間の依頼
  → 司令塔（目的・大きな方針の受領時）: 目的に対する位置を点検
  → PM: 要求・制約・完了条件を整理
  → QUESTION: 不確実な点だけ調査
  → PM: TASKSへ記録し実装単位を決定
  → IMPLEMENTER: 実装・局所検証・報告
  → REVIEWER: 独立レビュー
      ├─ PASS → PMが受入・文書更新・完了報告
      ├─ FIX_REQUIRED → IMPLEMENTERへ戻して再レビュー
      ├─ HUMAN_DECISION → 人間へ選択肢を提示
      └─ BLOCKED → 条件を記録し解消を待つ
```

司令塔は、タスク完了報告の前、担当切替の前、区切りにも点検を行う。点検は報告のみで、受入判定はPMが行う。

## 新規導入（init）

1. `PROJECT.md` の目的、対象者、非対象を確定する
2. `ARCHITECTURE.md` に最初の構成と制約を書く
3. 最小の利用価値を縦に通すタスクを `TASKS.md` に置く
4. 実装、レビュー、受入を小さく反復する

## 途中導入（adopt）

1. 既存のコード、設定、テスト、文書、Git差分を変更せず調査する
2. 現在の主要機能、起動・テスト方法、外部連携を `PROJECT.md` と `ARCHITECTURE.md` に補完する
3. 文書と実装の差は、直ちにどちらかへ寄せず `TASKS.md` に確認事項として残す
4. 導入前の未コミット変更を保護し、最初のタスク範囲から除外または明示する
5. 全体レビューを行い、設計との差分を優先度付きで整理する

## 役割分離の実現方法

利用環境が複数エージェントやworktreeを提供する場合は、実装とレビューを分離する。提供しない場合でも、レビューでは実装者の報告ではなく、タスク、差分、テストを最初から読み直す。

## タスクトラッカー連携（標準: Linear）

`TASKS.md`を正本としたまま、既定でLinearへ**手動・一方向の表示ミラー**を反映するのを標準とする。認証情報や既定のworkspace・team・project・issue IDは、この節のためにあらかじめ設定・埋め込まず、導入先が自分で用意する。

**Linearが使えない場合**（未認証・接続不可・権限不足）は、別経路へ切り替えず停止する。実際のエラー内容と、復旧に必要な対応（認証、接続、権限など）を代表へ報告し、選択肢（復旧を待つ、代表が扱いを決める等）を示す。「反映保留」として`TASKS.md`だけで作業を続けない。正本が`TASKS.md`である点は変わらず、Linearを正本にはしない。導入先がLinearを利用しない（導入していない）場合は、この標準の対象外とする。

新規のLinear project等の構成を初回に作成する操作は外部への書込みであるため、実行前に代表へ確認する。

### 基本原則

- 正本は常に`TASKS.md`（タスクの状態・実行記録）と`DECISIONS.md`（重要な判断）。トラッカー側の表示や、トラッカー上で人が直接行った変更を正本として採用しない。
- トラッカーへ送る情報は、タスクの存在（タスク番号と短い名称）、状態、定義済みの優先度に限る。詳細な実行ログ、差分、判断根拠、認証情報、秘密情報は送らない。
- 1つのタスク番号に対応するトラッカー側の項目（issue等）は1件とする。過去タスクの一括登録は行わない。
- タスク番号を主IDとし、トラッカー側のIDは外部参照として`TASKS.md`の当該タスク節に併記する。
- 本節の標準はLinearだが、同種の一方向表示ミラーとして使える他のトラッカーにも適用できる。

### 反映手順

1. 先に`TASKS.md`の対象タスク節を更新し、その後でトラッカー側へ反映する（逆順にしない）。
2. 対象のproject（導入先がprojectを使っていない場合は対象チーム）内に限定して、タスク番号を含む既存項目を検索する。同じチーム内の別projectに同じタスク番号の項目がありうるため、他projectの項目は更新・重複扱いしない。0件なら1件作成し、1件なら更新し、2件以上見つかった場合は書き込みを止めて人間またはPMへ報告する。
3. 作成・更新後は対象項目を再取得し、ID・タイトル・状態・優先度を読み返して、送った内容と一致するか確認する。
4. 一致を確認したら、`TASKS.md`の当該節にトラッカー側のID/URLと反映結果を記録する。以後、状態が変わるたびに`TASKS.md`を先に更新してから、同じ項目へ反映する。

### 失敗時と再開

- 認証切れ、接続失敗、権限不足、保存失敗が起きた場合は、別経路へ切り替えず、着手・状態変更を伴う開発作業を停止する（読み取り・調査は止めない）。失敗した時点の操作段階と実際のエラー内容（秘密情報は含めない）を代表へ報告し、選択肢を示す。`TASKS.md`は正本のまま変わらず、Linear側の状態を正本として扱わない。
- 復旧後は検索からやり直し、既存項目を再利用して重複を作らない。読み返しで一致を確認できた時点で停止を解除し、作業を再開する。
- トラッカー側で人が直接内容を変更した場合も、正本へ自動的に採用しない。必要な変更は先に`TASKS.md`へ反映してから、改めて一方向でトラッカー側へ反映する。

### 独立レビューでの確認

- REVIEWERは、実装者の「反映した」「確認した」等の自己申告だけでは判定しない。可能であれば自分自身でトラッカーへアクセスし、対象項目を直接取得して`TASKS.md`の記録と一致するか確認する。
- トラッカーへの独立アクセス手段がない場合は、その限界を明記し、確認できた範囲とできなかった範囲を区別して判定する。
